## 1. 已对齐的范围与结论

用户已选择「等待动画＋首段衔接」：发送后到本轮首段正文出现前有持续反馈；首段到来时平滑结束等待动效，正文继续即时显示。后续正文追加、Markdown 块转换不增加逐字、逐段淡入，也不增加强制等待时长。

当前确实缺少聊天内容区的等待动画。不能笼统说整个页面没有动画：发送请求中的按钮转圈、历史加载骨架和本地发送气泡淡入已经存在，但不覆盖请求完成后等待上游首段回复的阶段。

| 位置 | 当前行为 | 证据 |
| --- | --- | --- |
| `ConversationContent.kt:270` | `isRunning` 时直接插入静态「正在回复…」；结束直接移除 | 普通 `Text`，没有循环或进退场动画 |
| `ChatComponents.kt:854` 的 `SendAction` | 请求发送中/停止中有进度圈；生成期间显示停止按钮 | 按钮状态不能代替内容区等待反馈 |
| `ConversationContent.kt:188` | 首载或消息列表尚未准备完成时显示骨架 | 与本轮等待首段不是同一种状态 |
| `ConversationContent.kt:243` | `local:` 消息有 180 ms 淡入 | 只作用于本地发送消息 |
| `ConversationContent.kt:543` | 执行过程标题显示「执行过程 · 进行中」 | 进程状态文字不是回复等待动画 |

运行证据：API 37 模拟器中挂载真实 `ConversationContent`，输入一条固定用户消息、`isRunning=true`、尚无 agent 正文，稳定后每 160 ms 截取一次列表，共 8 次、跨度 1,280 ms。与基准图相比，变化像素数为 `[0,0,0,0,0,0,0,0]`。诊断断言「等待应有可见动效」按预期失败，这是缺失动效的复现证据，不能当作修复验收通过。

诊断源码、Gradle 注入脚本、构建日志、失败日志和截图均在项目忽略目录 `.verification/2026-10-14-reply-wait/`。仅覆盖安装测试 APK，没有发送真实消息、修改网关或部署产品修复。截图为隔离组件画面，不是完整聊天页面的视觉验收。

## 2. 交互规格：位置、时机、尺寸与退出

以下数值为实施起点，尚未经过真机视觉验收。

| 阶段 | 显示与动画 | 触发和退出 |
| --- | --- | --- |
| 发送已被本地接受，等待首段 | 原 `reply-progress` 位置显示原生小进度圈＋「正在回复…」；状态行先出现，圈持续旋转 | 本轮本地消息进入列表即开始，不等待 HTTP 返回；不因发送按钮结束转圈而停止 |
| 只有思考/工具过程，没有正文 | 同一状态行继续反馈；已有执行过程面板照常显示，不额外给面板加第二个圈 | 不能把工具步骤或旧回复误当成本轮首段 |
| 本轮首段正文准备完成 | 正文当次立即显示；等待圈在 120 ms 内淡出，文字保持静态「正在回复…」 | 以后台解析后的当前轮可显示内容进入 `renderItems` 为准，不以收到 WS、`streamingMessageId != null` 或计时器为准 |
| 后续正文持续到达 | 保留静态状态行，沿用现有即时 Markdown | 不重播首段衔接，不为每次快照启动动画 |
| 正常结束或停止已确认 | 状态行 120 ms 淡出并同步收起占位，退出完成后移除列表项 | 新正文不等退出动画；结束早于首段也可直接退出 |
| 等待确认、断连、发送失败、停止中 | 立即停掉「正常等待回复」循环，按下文规则交给已有提示或停止状态 | 状态含义优先于未播完的动画 |

布局沿用当前左对齐位置、顶部 `12.dp` 间距、`14.sp` 字号、`SecondaryInk` 文本颜色。复用已有 Compose 原生进度组件，建议圈 `16.dp`、线宽 `2.dp`、与文字间距 `8.dp`；颜色复用项目强调色。首段衔接期间和后续生成期间保留圈的空槽，文字不左右跳动。圈与文字组成一条状态，不引入插画、SVG、位图或动画依赖。

仅图标淡出，正文不淡出、不缩放、不等待。首段很快到来时不强制展示完整一圈；若该帧已经有本轮正文，直接呈现正文与静态状态。状态行在列表底部，首段插入其前方；不把这次正常列表增长包装为整条回复入场动画。

## 3. 状态判断与边界

`ConversationContent` 目前只收到 `isRunning`、`streamingMessageId`、`waitingForConnection` 等信息，不能独立区分审批、停止与新一轮。应从 `ChatDemoScreen` 传入所需的现有状态，集中派生最少的显示条件；不建立通用动画状态机、不新增后端枚举。

优先顺序与处理：

1. 当前会话切换、离开页面：取消旧动画和旧轮次记录。利用现有会话 `key` 和异步结果隔离；同会话重新进入也不能接收旧访问的延迟解析结果。
2. `waitingForConnection` 所代表的消息同步错误/实际断网：停掉正常等待循环，复用已有断连提示、重试入口及历史保留行为。不能仅凭 WS 状态就声称整个服务不可用，沿用已有连接可用性判断。
3. 当前轮发送失败：停掉等待，保留现有错误和草稿恢复。不能把全局其他操作错误都当成发送失败。
4. `isStopping`：状态行静态显示「正在停止…」，复用按钮已有转圈，避免重复循环。取消请求成功并同步确认结束后退出；停止失败则根据真实运行状态恢复等待或正文状态，不提前显示结束。
5. `pendingInteraction` 或待方案确认：使用现有交互/方案面板，移除回复等待行。用户提交期间沿用面板的提交反馈；实际恢复运行后再依据本轮是否已有正文决定是否转圈。
6. 当前轮仍在运行且没有可显示正文：循环等待；有正文：静态生成状态；不再运行：退出状态行。

### 本轮身份与首段定义

- 不能用「会话中存在任意 agent 正文」判断首段，否则第二轮发送会被上一轮回复直接短路。
- 以本次发送边界和现有本地消息/服务器消息的确认关联为依据；本地 `local:` ID 替换成服务器 ID 不能变成第二次发送。先复用现有 `outgoing` 对账能力，只有现有信息不足时才补最小的本轮标识，不按相同文本猜身份。
- 接入已运行的会话时，依据当前轮实际内容恢复状态；已有正文不重播首段动画。仅 `streamingMessageId == null` 不代表尚无正文，初始化快照、等长修正和重连都可能出现这个值。
- 本轮正文指可显示的 agent 回复内容，包括可显示的非文本回复；空白正文、思考、工具执行卡不算最终回复首段。使用实际准备后的列表项判定，避免 WS 已到但后台解析未完成时先清空等待。
- 当前轮一旦已有正文，该轮后续修正、正文临时为空或重连不重新进入「首段等待」；暂停后恢复也不重播。新一轮才重置。
- 排队发送只入队时不重置正在执行轮次的等待状态。队列真正成为新一轮后才按新一轮处理；历史分页、加载旧消息不重置。

其他直接调用还包括 `ExecutionPanelTest`、`ReplyMediaAndCopyTest`、`LocalImagePreviewTest`；变更签名前再次全仓搜索 `ConversationContent(`。若新增非平凡轮次判断函数，补小型 JVM 状态序列测试；无需为常量或纯视觉参数另写单测。无需新增依赖、配置、导出、后端协议或请求拦截器。

列表收尾需要一起调整：当前自动跟随的末项计算直接依赖 `isRunning`（约第 199 行）。退出动画期间行仍存在时，滚动逻辑应以实际参与布局的状态项为准，不能在 `isRunning=false` 时提前当它不存在，也不能等循环动画每帧都滚动。保持 `followLatest`、历史锚点、执行过程展开和回到底部按钮的原有语义。

使用项目已有 Compose 动画能力。透明度在绘制阶段更新，循环不能触发全文解析、列表重建或网关轮询；退出动画结束才移除状态项，透明内容退出时清掉无效语义。官方说明见 [Compose 动画快速指南](https://developer.android.com/develop/ui/compose/animation/quick-guide) 和 [值动画](https://developer.android.com/develop/ui/compose/animation/value-based)。

无障碍与生命周期：文案稳定，装饰性圈不重复朗读；不按动画帧变更 TalkBack 内容。遵守现有 `MotionDurationScale`，关闭动画时保持清晰静态状态且立即完成衔接；运行途中关闭也必须生效。页面退后台、状态行离开实际可见区时暂停循环，返回后按当前真实阶段恢复，不能启动新的轮次。暂停不能造成首段不可见。长等待不显示虚假进度百分比，也不凭时间宣称服务故障。

## 5. 提交与验收颗粒度

### 第一步：轮次与显示条件

交付：接通最少状态，确认本轮首段判定和优先级；业务请求逻辑不变。

验收：新发送、旧回复存在、本地 ID 确认、已运行会话进入、断连恢复、审批恢复、排队切轮和切会话的状态序列。若需要修改 ViewModel，必须验证停止失败、发送失败及旧回调不会改变新会话。

建议提交：`refactor(android): 明确回复等待与首段显示状态`。

### 第二步：等待圈与首段衔接

交付：同一状态行增加原生圈；首段即时显示、圈 120 ms 淡出；结束行淡出收起；修正退出期间末项定位。状态逻辑若只有数行，可与第一步合并成一个完整提交。

验收：等待多帧像素确实变化，文字与行边界不随转圈改变；首段到达的同次 UI 更新即可找到正文，不需推进 120 ms 动画钟；随后正文追加不再触发等待圈。结束后状态行、动画任务和语义节点全部消失。快速开始/结束及结束中开始新一轮也正确。

建议提交：`feat(android): 增加回复等待动画与首段衔接`。

### 第三步：交互回归与设备验收

| 场景 | 通过标准 |
| --- | --- |
| 发送后长时间无正文；仅有工具/思考 | 等待反馈持续可见，不整屏骨架、不虚构进度、不重复动画圈 |
| 快速首段；首段与结束同一快照；没有正文即结束 | 不设置最短等待；正文直接出现；无残留圈或永久空白状态项 |
| Markdown 标题/代码/图片等首个可显示块 | 真正可显示才衔接；继承已有生成中富文本能力 |
| 第二轮发送、ID 确认、排队、重连、历史分页 | 不误用上一轮正文，不重复衔接，不因分页重新等待 |
| 审批、停止成功/失败、发送失败、断网/恢复、切会话 | 状态与真实任务一致，没有无限「正在回复」或旧回调串会话 |
| 阅读历史、展开执行过程、回到底部、键盘开合 | 不强制拉回底部；正常跟随时无返回按钮闪现；收尾无错误索引 |
| 320/360/412 dp，字号 1.0/1.5 | 圈不挤压文字、不裁切；首段衔接文字不横跳 |
| 关闭系统动画，运行中关闭，TalkBack | 静态反馈清晰、正文及时显示；仅阶段改变触发必要播报 |
| 后台/回前台、滚出可见区/回来 | 无不可见循环持续消耗；回来不重播已完成的首段衔接 |

执行顺序：相关 JVM 测试、Debug/AndroidTest 构建、聚焦新增用例、既有流式/执行过程/复制/历史锚点/关闭动画回归。逐帧测试用受控时钟，避免无限动画导致 `waitForIdle` 等待错误；另外录制实际播放以核对节奏。确认仅等待动画期间没有新增 Markdown 解析或网络调用。

最后在真实设备核验亮暗色、字体比例、键盘和长等待的实际观感；模拟器通过不能等同于真机流畅。目前真机未连接，本轮没有完成该项。此计划不改网关 250 ms 轮询，不重新部署网关；首字网络延迟与动画体验分开评价。

建议最终记录提交：`docs: 记录回复等待动画验收结果`，同时更新 `Agent.md`。本文件中的实施与验收项目当前均为待执行，唯一已完成运行检查是修复前静态等待的复现。

## 6. 实施与验收记录

### 已实现

- `ConversationContent` 的等待行接入原生 `16.dp` 进度圈，保留 `14.sp` 文案和固定图标槽位。`ReplyProgress` 复用现有颜色和 Compose 组件，没有增加依赖或图片素材。
- 当前轮可显示正文准备完成后，正文直接进入列表，圈在 120 ms 内淡出；本轮后续修正、正文临时清空和断连恢复不会重播首段等待。等待圈不以 HTTP 发送完成或 `streamingMessageId` 是否存在为依据。
- 已有消息分组足够表达本轮边界，无需修改 ViewModel 或后端。本地消息确认使用既有对账结果；新用户消息开始新一轮。补载到此前缺失的用户边界时，保留仍属于当前轮的已显示正文，避免历史分页重播等待。
- `ChatDemoScreen` 接入停止与审批状态。断连/消息错误沿用现有提示；审批隐藏等待行；停止期间静态显示「正在停止…」，停止优先于审批，停止失败按真实状态恢复。普通发送失败沿用已有运行态回退和草稿恢复。
- 正常结束时状态行淡出并收起，末项滚动索引包含退出中的状态行。离屏结束直接移除，不等待未参与绘制的列表项完成动画；历史阅读锚点保留。
- 实际不可见、页面未处于 RESUMED 或系统动画比例为零时，用静态进度弧替代无限动画。装饰圈不提供重复无障碍内容，退出的状态行清理语义。
- 动画状态不进入后台 Markdown 解析的 `LaunchedEffect` 参数；代码未增加接口、轮询、Markdown 缓存或请求日志路径。本轮没有修改或部署网关，也没有操作真实会话的发送、停止或审批。

# 真机聊天快滑卡顿排查（2026-10-02）

## 环境与范围

- USB 真机 vivo V2339FA，Android 16，1260 × 2800。
- 使用用户刚通过 Android Studio Run 安装的当前开发包；没有重装、清空数据或修改性能代码。
- 目标为“新建测试窗口”的长富文本回复。界面原本位于该回复末段。
- mgy 在 58900 端口运行，健康检查返回 200；本轮没有停止、重启或修改网关。

## 复现与测量

在已打开的测试会话中，重置 gfxinfo，向历史方向快速滑动 10 次，再向最新方向快速滑动 10 次；两轮都出现孤立慢帧。

| 指标 | 第一轮 | 已预热的第二轮 |
| --- | --- | --- |
| 渲染帧数 | 1168 | 998 |
| gfxinfo Janky frames | 1 | 1 |
| gfxinfo legacy Janky frames | 22 | 20 |
| P50 / P95 / P99 | 6 / 9 / 19 ms | 7 / 10 / 38 ms |
| GPU P95 / P99 | 5 / 7 ms | 5 / 6 ms |

不同统计口径的掉帧计数不能混用。该问题表现为少数帧明显停顿，整体平均流畅度较高。

第二轮同时采集 Perfetto 的 gfx/view/input/dalvik、线程调度和 FrameTimeline：

- 两个 Choreographer 帧分别耗时 **41.635 ms** 和 **43.655 ms**。
- 对应 `AndroidOwner:measureAndLayout` 耗时 **35.029 ms** 和 **33.257 ms**。
- 这两个布局片段分别包含 **90** 和 **84** 次富文本 Text 节点测量，累计约 **15.54 ms** 和 **14.12 ms**；此外还有重组及应用组合变更的成本。各嵌套片段不可直接相加。
- 35.029 ms 的布局期间，主线程调度状态始终为 `Running`，没有明显被抢占或阻塞。
- 紧邻第二个慢帧之前有 **15.139 ms** 的 `compose:lazy:prefetch:execute:urgent`，其中约 **14.999 ms** 为预组合。
- RenderThread 最长 `DrawFrames` 约 **5.36 ms**；没有采集到该应用的 GC 片段。
- FrameTimeline 中应用超期的帧总耗时最高 **48.75 ms**；该设备应用预期帧预算为 **11.6 ms**。
- 录制末尾由 UIAutomator 查询触发的语义树片段不作为用户滚动卡顿证据。

## 结论与边界

已确认本次快滑慢帧的主要耗时在 **Compose 组合与测量布局**，足以产生短暂停顿。以一整条超长回复作为一个 LazyColumn 项，导致进入视口时一起处理大量文本节点，是与源代码及轨迹均一致的原因。

现有 40 条 Markdown 后台预解析和 80 项 AST 缓存只减少语法解析成本，不能省去这批布局工作。重复滑动已预热内容仍出现慢帧，增加解析缓存数量不能单独解决本次问题。

本次没有精确到每个 Markdown 块的函数追踪标记，所以无法把两帧分别绑定到具体消息 ID；也不能据此宣称公式图像更新完全没有额外成本。GPU、GC 和系统抢占不是这两个已捕捉慢帧的主要原因。

建议优先将超长正文的顶层 Markdown 块拆为同一 LazyColumn 内的稳定列表项，按视口加载，并保留消息级复制、附件、顺序和折叠语义；再依据同一路径复测是否还需要额外预取。当前没有实现该修改。
